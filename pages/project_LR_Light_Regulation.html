Project Overview

Project Description

Et intelligent belysningssystem designet til at optimere energiforbrug gennem automatisk lyskontrol baseret på tilstedeværelse og naturligt lys. Systemet kombinerer Arduino Mega 2560 til sensor- og LED-styring med Raspberry Pi til avanceret databehandling og grafisk interface.

Objectives

  • Automatisere belysning baseret på tilstedeværelse og naturligt lys med konsistent feedback-loop
  • Reducere energiforbrug gennem intelligent lysregulering og historiebevaring
  • Implementere en modulopbygget pipeline-arkitektur med klare ansvarsgrænser
  • Sikre pålidelig UART-kommunikation mellem Arduino og Raspberry Pi
  • Tilbyde real-time diagnostik og brugervenlig mode-kontrol (auto/manual/regulating)

Key Features

Adaptiv Lysregulering

Dynamisk justering af lysintensitet baseret på tilstedeværelse, tidsvindue og naturligt lys måling.

Struktureret Historik

NumPy-baseret tilstandslager som bevarer fuldstændig datahistorik for analyse og debugging.

Centraliseret Logik

Alle lyskontrol-beslutninger i én Processor klasse - undgår distribueret og redundant kode.

UART Pipeline

Robust seriel kommunikation mellem Arduino og Raspberry Pi med error handling og connection resilience.

Intelligent Mode-kontrol

Brugervenlig styring af Auto/Manual/Regulating modes med enkel abstraktion og klare overgange.

Arkitektur: Pipeline-Model med 6 Komponenter Documentation

Arkitektonisk Design

Systemet implementeres som en klassisk pipeline-arkitektur: Data flows envejen gennem komponenter, hvor hver transformerer input til output for næste komponent. Dette sikrer:

  • Separation of concerns - hver klasse har ét klart ansvar
  • Testabilitet - hver komponent kan enhedstestes isoleret
  • Vedligeholdelse - ændringer i én komponent påvirker ikke andre
  • Udvidelse - nye features tilføjes uden at modificere eksisterende kode

De 6 Komponenter

Raspberry Pi (Python) - Min Primære Bidrag:

  • 1. UART Driver - Seriel kommunikation (read/write) med Arduino
  • 2. Data - NumPy-baseret struktureret historiklager
  • 3. Processor - Centraliseret lyskontrol-logik og beslutninger
  • 4. Router - Kommando-routing og tilstandsændringer (testing & bug-fixing)

Raspberry Pi (Python) - Andre Komponenter:

  • 5. GUI - Brugergrænsefladen med slider, mode-knapper, status-display
  • 6. Developer GUI - Diagnostik, datavisning, health-check, test-data injection

Arduino (C++) - Min Sekundære Bidrag:

  • UART Driver (OOP refactoring) - Kommunikation med Raspberry Pi
  • Router - Kommando-routing og sensor-broadcasting

[Arduino UART] → (serial port) → [Raspberry Pi UART Driver]

Data Klasse - Central State Storage Documentation

Formål og Design

Data-klassen fungerer som systemets centrale tilstandslager. Den bevarer fuldstændig historik over alle systemtilstande ved at oprette nye datapoint ved hver ændring, i stedet for at overskrive eksisterende data.

Denne tilgang sikrer, at historiske data altid er tilgængelige for analyse, mens det nyeste tilstand forbliver let tilgængeligt.

Datastruktur

Internt bruger Data-klassen en NumPy-struktureret array til effektiv lagring:

FeltBeskrivelseType
luxNaturligt lys måling (lux)int
motionBevægelsesdetekteringbool
currentEnergiforbrug (mA)float
light_intensityLED intensitet (0-100%)int
light_autoAutomatisk mode aktivbool
light_regulatingReguleringstilstand aktivbool
timeTimestampdatetime
light_onLED'er tændt/slukketbool

Vigtige Metoder

# Tilføj nyt datapoint
data.add(lux=450, motion=True, current=125, light_intensity=75)

# Hent alle datapoints
all_points = data.get_data()

# Hent datapoints inden for tidsinterval
recent = data.get_data(start_time=now - timedelta(hours=1))

# Filtrer specifikke felter
lux_values = data.get_data(filter=['lux'])

Løste Problemer

Filter-håndtering: Hvis et enkelt filtrerværdi blev passeret som string, blev det tolket som tegn-sekvens. Løsningen normaliseredes inputtet, så enkelværdier altid blev behandlet som ét felt.

Single-result Inkonsistens: Når kun ét datapoint blev returneret, returnerede funktionen nogle gange et enkelt objekt i stedet for en liste. Løsningen sikrer altid et list-return, selv for ét datapoint.

Processor Klasse: Centraliseret Kontrollogik Documentation

Arkitektonisk Betydning

Processor er hjerte af systemet. Den modtager indgående data (sensordata eller brugerbeslutninger), men kræver IKKE alle felter. Hvis et felt ikke er specificeret (None), slår Processor det op fra historikken og bevarer tidligere værdi. Dette muliggør partielle state-updates.

Kritisk designbeslutning: ALLE lyskontrol-beslutninger centraliseres her. Processor indeholder al logik til at bestemme on/off-tilstand og lysintensitet. Dette undgår redundant logik spredt på tværs af GUI, Router og andre komponenter.

  • GUI kan sende kun slider-ændringer (light_intensity). Processor bruger eksisterende motion, lux, mode fra Data.
  • Arduino kan sende kun sensor-værdier (lux, motion, current). Processor holder eksisterende light_on, light_regulating status.
  • System bevarer automatisk tilstand uden at komponenter behøver at håndtere state-kombinatorik.

Processor.add() Implementering

class Processor:
    def __init__(self, data):
        self._data = data
    
    def add(self, lux=None, motion=None, current=None, light_intensity=None,
            light_auto=None, light_regulating=None, fixed_intensity=None, light_on=None):
        """Transformerer input til ny systemtilstand."""
        
        AUTO_TIME_THRESHOLD = 60 * 5  # 5 minutter
        
        # Få nuværende state
        [auto, regulating] = self._data.get_data(item_name_filter=("light_auto","light_regulating"))
        
        if light_auto is None:
            light_auto = auto
        if light_regulating is None:
            light_regulating = regulating
        
        # BESLUTNING 1: Skal lyset være tændt eller slukket?
        if light_auto:
            if motion == True:
                light_on = True
            else:
                recent_motion = self._data.get_data(
                    interval=(time.time() - AUTO_TIME_THRESHOLD, time.time()),
                    item_name_filter=("motion",)
                )
                light_on = any(recent_motion) if len(recent_motion) > 0 else False
        else:
            if light_on is None:
                light_on = light_intensity > 0 if light_intensity is not None else self._data.get_data(item_name_filter=("light_on",))[0]
        
        # BESLUTNING 2: Hvor intens skal lyset være?
        if light_on:
            if fixed_intensity is None:
                fixed_intensity = self._data.get_fixed_intensity()
            
            if light_regulating:
                if lux is None:
                    lux = self._data.get_data(item_name_filter=("lux",))[0]
                light_intensity = self.calculate_intensity(lux, fixed_intensity)
            else:
                light_intensity = fixed_intensity
        else:
            light_intensity = 0
        
        data_point = self._data.add(lux, motion, current, light_intensity,
                                    light_auto, light_regulating, fixed_intensity, light_on)
        return data_point
    
    def calculate_intensity(self, lux, fixed_intensity):
        """Jo mere naturligt lys, jo mindre kunstig lys."""
        return min(255 - lux, fixed_intensity)

To Vigtige Logik-beslutninger

1. On/Off Bestemmelse: AUTO-mode tjekker for bevægelse indenfor 5-minutter. MANUAL-mode er bruger-kontrolleret.

2. Intensitet Bestemmelse: REGULATING justerer dynamisk baseret på lux. FIXED bruger brugerdefineret værdi.

Router Klasse - Central Routing Documentation

Rolle i Systemet

Router er det centrale routingpunkt der forbinder:

  • UART (Arduino kommunikation)
  • GUI (bruger input)
  • Developer GUI (diagnostik)
  • Processor (logik)
  • Data (state storage)

Primære Udfordringer

UART kommunikation ankommer som strings. Router skal derfor:

  • Identificere kommandotypen
  • Validere string-formatet
  • Parse datapoint-værdier
  • Konvertere til korrekte datatyper
  • Forward til Processor eller relevant komponent

Centrale Metoder

  • add(requested_state) - Sender state-ændring gennem Processor, får resultat, gemmer i Data, returnerer ny state til GUI/UART
  • uart_rout(uart_string) - Parser Arduino-besked, identificerer kommandotype (L/M/C/H/I/A), kalder add() eller health_check()
  • get_data(filters) - Henter historiske data fra Data-klasse, bruges af Developer GUI til analyse
  • remove_data(index) - Sletter datapoint fra historik
  • health_check() - Returnerer systemstatus (forbindelse, sensorer, data consistency)

Implementerings Aspekter

State Flow: GUI → Router.add() → Processor → Data → Router returnerer ny state til GUI. Reverse: Arduino UART → Router.uart_rout() → samme flow.

Data Retrieval: Developer GUI kalder Router.get_data(), som queries Data-klasse historik. Router er transparent forwarder, Data-klasse ejer al state.

UART Communication: Raspberry Pi ↔ Arduino Documentation

Raspberry Pi UART Driver

class Uart_driver:
    """Driver for UART serial communication with Arduino."""
    
    def __init__(self, port="COM19", baudrate=9600, timeout=1):
        try:
            self.ser = serial.Serial(port, baudrate, timeout=timeout)
        except serial.SerialException as e:
            print(f"Error: {e}")
            self.ser = None
        
        if self.ser:
            self.ser.reset_input_buffer()
            time.sleep(1)  # Wait for Arduino reset
    
    def write(self, data) -> None:
        """Send data to Arduino with newline termination."""
        if self.ser is None:
            return
        
        try:
            if isinstance(data, str):
                data = data.encode()
            self.ser.write(data)
            self.ser.write(b'\n')
        except serial.SerialException:
            self.ser = None
    
    def read(self):
        """Read one line from Arduino (until newline)."""
        if self.ser is None:
            return None
        try:
            line = self.ser.readline().decode('utf-8').strip()
            return line if line else None
        except (serial.SerialException, UnicodeDecodeError):
            return None

Kommunikationsprotokol

# Arduino → Raspberry Pi (single-character prefix + data)
L230           → Lux sensor reading
M1             → Motion detected (1=true, 0=false)
C125           → Current reading
L450|M1|C125   → All sensor data at once (from A command)

# Raspberry Pi → Arduino (commands)
H              → Health check (Arduino responds with 'H')
I75            → Set intensity to 75
L              → Request lux reading
M              → Request motion status
C              → Request current reading
A              → Request all sensor data

Kritiske Løsninger

Problem: Program crash uden Arduino tilsluttet
read() blokerede uendeligt hvis Arduino ikke var tilsluttet.
Løsning: Connection check, try/catch, return None if disconnected. Tillader udvikling uden hardware.

Problem: Partial messages
Hvis UART data kom i flere chunks, var message ufuldstændig.
Løsning: read() blocker indtil newline modtages.

Testing Strategi og Resultater Documentation

Teststrategi

Enheds-testing blev brugt selektivt. Mange klasser var tæt koblet, så isoleret testing ville krævet mange stubs. Større vægt blev derfor lagt på integration testing.

Debugger blev også brugt til step-through eksekution for at identificere hvor inputs resulterede i uventet output.

Processor Testing

# Test Processor med forskellige input-værdier
test_cases = [
    {'motion': True, 'lux': 100, 'mode': 'auto', 'expect_light': True},
    {'motion': False, 'lux': 800, 'mode': 'auto', 'expect_light': False},
    {'motion': False, 'lux': 100, 'mode': 'manual', 'set_intensity': 50, 'expect_intensity': 50},
]

for case in test_cases:
    result = processor.process(case)
    assert result['light_on'] == case['expect_light']

UART Testing

Tidlig testing: Arduino IDE serial monitor tilføjede automatisk carriage return efter newline, hvilket fik protokol til at mismatch.

Løsning: Testing blev moved til direkte Raspberry Pi ↔ Arduino integration. Integration tests viste stabil kommunikation uden observeret datatab.

Hardware Arkitektur Documentation

System Layout

Hardwaren var split i separate moduler frem for én PCB. Dette tillod moduler at være placeret på forskellige fysiske lokationer og gjorde debugging lettere.

  • Arduino Mega 2560 - sensor og LED kontrol
  • Raspberry Pi + touch display - data processing og GUI
  • ACS712 current sensor - strømmåling
  • Operationel forstærker - current signal amplification
  • LED/transistor modul - lyscontrol
  • Motion sensor - bevægelsesdetektering
  • Light sensor (LDR) - naturligt lys måling

UART Forbindelse

Raspberry Pi og Arduino kommunikerer gennem crossed UART forbindelse.

Arduino TX (pin 18) → Raspberry Pi RX (GPIO 15)
Arduino RX (pin 19) ← Raspberry Pi TX (GPIO 14)
Common GND

Kritiske Designbeslutninger

Strøm Sensor: ACS712 producerede kun små spændingsændringer ved lav LED-strøm. Operationel forstærker blev tilføjet for at øge måleområde, men introducerede støj der reducerede nyttelighed.

LED Kontrol: Otte LED'er drevet gennem BD139 NPN transistor i stedet for direkte Arduino pins. 24mA per LED med 63Ω modstand. 470Ω base-modstand for transistor. Danner basis for PWM lys-intensitet kontrol.

Project Conclusion

Results

Systemet arbejdede som forventet. Lysreguleringen aktiverede og deaktiverede automatisk baseret på tilstedeværelse med korrekt tidsvindue, og justerede lysintensitet dynamisk efter naturligt lys. Mode-switching mellem Auto/Manual/Regulating virked pålideligt. Kommunikationen mellem Arduino og Raspberry Pi var stabil, og systemet bevarte fuld historik uden datakab. Projektets primære mål blev opnået: automatisk energieffektiv lyscontrol med brugervenlig betjening.

Lessons Learned

Over-modellering af statespace er farligt. Initialt designede vi en kompleks to-dimensional state machine med mange tilstande. Efter flere iterationer blev det klart, at denne kompleksitet var helt unødvendig—simple boolean-flags løste problemet bedre. Lektie 1: Start altid minimal, og tilføj kompleksitet kun når den er berettiget. UML-kode alignering er kritisk. Når arkitekturen i diagrammer ikke matchede koden, opstod confusion mellem komponenter og deres ansvarsgrænser. Vi måtte refaktorere for at få dem til at stemme overens. Lektie 2: Diagrammer skal være levende dokumentation, ikke abstrakt kunst. Små, fokuserede komponenter slår et stort system. Router-klassen blev det problematiske punkt fordi den gjorde for meget. Opdeling af ansvaret gjorde debugging og testing signifikant lettere. Lektie 3: Hver klasse skal have ét klart ansvar. Hardware-valg skal valideres tidligt. ACS712 current sensor viste sig ukompatibelt først under test—hvis vi havde prototypet tidligere, havde vi fundet det straks. Lektie 4: End-to-end test med ægte hardware er uundværlig; simulering er ikke nok. Test-miljøer kan være misleadende. Arduino IDE's serial monitor tilføjede automatisk carriage return, som fik protokollen til at fejle. Kun når vi testede direkte Rpi↔Arduino blev det ægte problem synligt. Lektie 5: Test med de faktiske komponenter, ikke med dev-tools.

Future Improvements

  • Motion sensor hardware: Bedre kalibrering for pålidelig detection, muligvis dual-sensor redundance
  • Current sensor: Passivt RC-filter i stedet for opamp amplification (mindre støj)
  • Processor: Extract complex nested if-statements til navngivne helper-metoder
  • UART: Implementer timeout-based retry-logik for robusthed ved intermittent connections
  • Acceptance tests: Bedre specificering med klare preconditions, observable assertions, worst-case scenarios
  • Optimization: Deep sleep modes for lavere Raspberry Pi strømforbrug i idle-tilstand

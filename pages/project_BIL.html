Project Overview

Project Description

BIL-projektet er en indlejret systembillede til styring af et autonomt køretøj ved hjælp af en AVR-mikrokontroller. Systemet integrerer motorstyrings, lyscontrolitering, sensorinputbehandling og UART-baseret brugergrænseflade. Dette første-semester universitets projekt demonstrerer interrupt-drevet arkitektur, real-time state machine design og hardware abstraction principper.

Objectives

  • Implementere motor-styring med variable hastighedskontrol og retningsændring
  • Automatisere køretøj-sensorfeedback gennem refleksbrik-detektion for præcis positionsbestemmelse
  • Sikre lyskontrol med PWM-baseret intensitetsregulering for forlygte, baglys, og bremsekontrol
  • Tilbyde bruger-interface gennem UART-baseret menusystem til realtidskommandokontrol
  • Validere systemintegration af hardware-drivere og kommunikationsprotokoller under operationelle betingelser

Key Features

Motorkontrolsystem

PWM-baseret motorcontrol med gradual accelerationsprofiler, retningsvalg og glatte hastighedstransitioner for at forhindre mekanisk stød

Uafhængig Lyscontrol

Tre uafhængige lyskredsløb (for, bag, bremsekontrol) med PWM duty cycle kontrol for realistisk lysintensitetsmodulation

Refleksbrik-Baseret Positionering

Tæller-baseret køretøjspositionering ved hjælp af eksterne interrupts, adaptiv debounce-timing (200ms/500ms) og real-time state machine progression

UART Kommunikationsgrænseflade

Seriel kommunikation ved 9600 baud til menu-drevet kontrol, telemetritransmission og systemdebugning over terminal

Interrupt-Drevet Arkitektur

Effektiv asynkron hændelseshåndtering med timer-baseret debouncing, eliminering af sensorbounce og sikring af pålidelige state transitions

Arkitektur: Lagdelt indlejret systemdesign Documentation

System Architecture

BIL-systemet følger en klassisk indlejret systemarkitektur med klar adskillelse af bekymringer på tvers af tre lag:

  • Brugerinterface-lag - UART menu-system (_menuSYS, menu, kontrole) til manuel kontrol og debugging
  • Kontrollogik-lag - Hoved-event loop med state machine drevet af Refleks_count positionsvariabel (0-9)
  • Hardware Abstraction Lag - Modulare driverkomponenter (motor, lys, sensor, timer, UART) der indkapsler port-manipulation

Data Flow Pipeline

De tre vigtigste kontrolveje er adskilt i stedet for at blive beskrevet som én samlet pipeline: sensorinterrupts opdaterer kun tilstand, hovedloopet forbruger tilstanden, og UART-menuen er en separat manuel vej.

Interrupt flow
Sensorinput (Refleksbrik)
  ↓
INT0_vect / INT1_vect ISR
  ↓
Refleks_count++
EIMSK = 0b00000000
start_timer(200 | 500)
UNISendInteger(...)
  ↓
Timer5 overflow ISR
  ↓
EIMSK = 0b00000011
Main loop flow
while(1)
  ↓
Read Refleks_count
  ↓
Switch on state
  ├─ 0: initialization / menu waiting
  ├─ 1-6: progressive states
  ├─ 7-8: high-speed states
  └─ 9+: final states
  ↓
Apply motor / light / audio commands
UART menu flow
UART input
  ↓
_menuSYS()
  ├─ 'm' → menu()
  ├─ 0x01 → kontrole()
  └─ 0x02 → force next sensor step (debug)
          ├─ Refleks_count++
          ├─ EIMSK = 0b00000000

Manual Control Flow

Manual control should be read as a separate path from the sensor-driven state machine. `_menuSYS()` routes into `menu()` for interactive commands and into `kontrole()` for direct debug actions without waiting for the next reflective marker.

Manual command flow
Brugerinput
  ↓
_menuSYS()
  ↓
menu() or kontrole()
  ↓
motorPWM() / motorPWMGradvis()

SOMO_Play_*()
  ↓
UNISendInteger() / UNISendString() telemetry
  • menu() - Human-readable menu for set/get/debug interactions
  • kontrole() - Direct command dispatcher for test actions and state overrides
  • Telemetri - Echoes current values back over UART after command execution

Motordriver - PWM-Baseret Hastigheds- og Retningskontrol Documentation

Purpose and Design

Motordriveren administrerer alle motorstyringsoperationer ved hjælp af PWM (Pulse Width Modulation) på Timer0. Den sørger for både øjeblikkelig hastighedsændring og graduel accelerationsprofiler til at forhindre mekanisk stød og sikre glatte overgange. Driveren accepterer delvise statændringer - hastighed kan modificeres uafhængigt uden at påvirke retningsindstillinger.

Key Design Decision

Motordriveren kræver IKKE fuld initialisering på hver kommando. Når initMotor() konfigurerer Timer0 og retningspinne, modificerer efterfølgende motorPWM() eller motorPWMGradvis() opkald kun PWM duty cycle. Dette tillader menusystemet at justere motorhastighed til enhver tid uden at nulstille retning eller påtage sig initialiseringsomkostninger. Manglende eller uændrede parametre bevarer deres tidligere tilstand.

Main Functions

  • initMotor() - Engangs initialisering: konfigurerer Timer0 til PWM output, sætter retningskontrolpinne som digitale output, etablerer PWM frekvens
  • motorPWM(uint8_t speed, uint8_t retning) - Øjeblikkelig hastighedssændring: sætter motor PWM værdi (0-255 skalå) og retning. Speed=0 stopper motor. Retning: 0=bagud, 1=fremad
  • motorPWMGradvis(int16_t startSpeed, int16_t topSpeed, int8_t step, uint8_t retning, uint16_t delay_ms) - Graduel acceleration: glat ramping af motor fra startSpeed til topSpeed, inkrement PWM ved step værdi hver delay_ms millisekunder
  • motorIdle() - Stop motor: sætter PWM til 0, bevarer retning til næste kommando

Code Example

// From main.c - System initialization
initMotor();  // Configure Timer0 and direction pins once

// State 1: Gradual acceleration from rest
motorPWMGradvis(0, 200, 1, 1, 10);
// Start at 0 PWM, ramp to 200 PWM (forward direction)
// Increment by 1 every 10ms = 2 seconds total ramp time

// Menu system: immediate speed adjustment
motorPWM(150, 1);  // Jump to 150 PWM forward (no ramp)
motorPWM(0, 1);    // Stop immediately

// State 9: Motor idle
motorIdle();  // Set PWM to 0, direction preserved

Problems Solved

Problem: Direkte PWM spring forårsager pludselig acceleration, hvilket skaber mekanisk stød og vibration i motor og tandhjul.

Løsning: motorPWMGradvis() implementerer glat accelerations-ramp med konfigurerbar trin størrelse og forsinkelse mellem inkrementer, spredt hastighedssændring over flere tidsintervaller.

Problem: Ingen måde at teste motorcontrol uden at udløse sensor-baseret state machine.

Løsning: Menusystemet kan kalde motorPWM() og motorPWMGradvis() direkte til enhver tid, hvilket tillader uafhængig test af motoradfærd før sensor integrationstestning.

Lysdriver - Uafhængig PWM-baseret Lyskontrol Documentation

Purpose and Design

Lysdriver styrer tre uafhængige lyskredsløb ved hjælp af PWM duty cycle modulation til realistisk lysintensitets justering. Dette afspejler virkelig køretøj adfærd hvor baglys dimmers under normal drift og stiv op til bremsesignaler. Hver lys opererer på sin egen timer register med uafhængig kontrol.

  • Forlygte (Forlys) - Primær fremadrettet belysning
  • Baklys (Bag/Bremsely) - Bag indikator og bremsesignal
  • Baglys (Bakgear/Tilbagelys) - Gear bagud indikator

Key Design Decision

Hver lysfunktion accepterer KUN sin egen duty cycle parameter og modificerer KUN sit tilsvarende timer register. Dette design forhindrer utilsigtet interferens mellem lys og tillader state machine at kontrollere alle tre uafhængigt. I modsætning til til/fra kontrol muliggør PWM duty cycle realistisk lysintensitets modulation (0-255 skalå) hvor forskellige tilstande kan sætte forskellige intensiteter.

Main Functions

  • SetForlys(uint8_t dutyCycle) - Kontroller forlysintensitet: 0=fra, 255=maksimal intensitet
  • SetBaklys(uint8_t dutyCycle) - Kontroller bag bremsely intensitet
  • SetBaglys(uint8_t dutyCycle) - Kontroller tilbagelys intensitet

Code Example

// From main.c - System initialization (all lights off)
SetForlys(0);   // Front light: off
SetBaklys(0);   // Brake light: off
SetBaglys(0);   // Reverse light: off

// State 1 (acceleration): Lights on, moderate intensity
SetForlys(150);  // Front light: ~59% brightness
SetBaklys(100);  // Brake light: ~39% brightness
SetBaglys(0);    // Reverse light: remains off

// State 2-6: Progressive state transitions adjust lighting independently
// SetForlys(120); SetBaklys(80);  // Example state 2
// SetForlys(180); SetBaklys(150); // Example state 7 (higher speed)

// Reverse operation
SetForlys(0);    // Front off
SetBaklys(0);    // Brake off
SetBaglys(200);  // Reverse light: ~78% brightness

Problems Solved

Problem: Simpel til/fra lys matcher ikke rigtig køretøj adfærd hvor baglys dimmers under normal drift og stivner op til bremsesignaler.

Løsning: PWM duty cycle tillader lysintensitets modulation fra 0-255, muliggørende realistisk intensitetskontrol der matcher forventet køretøj lyser adfærd ved forskellige hastigheder og tilstande.

Problem: Tre uafhængige lyskredsløb kræver isoleret kontrol uden krydsforstyrrelser.

Løsning: Separate funktioner for hver lyskreds løb, hver modificerer kun sit eget timer register, forhindrer utilsigtet interferens og tillader samtidig uafhængig lysintensitets justeringer.

Sensorhåndterer - Interrupt-Drevet Refleksbrik Detektion Documentation

Purpose and Design

Sensorhåndtereren administrerer ekstern interrupt behandling til refleksbrik detektion. Når køretøjet passerer over en reflektiv markering, udløses en ekstern interrupt (INT0 eller INT1), som inkrementerer en global positionstæller. Systemet starter derefter en timer-baseret debounce mekanisme til at forhindre flere tællinger fra en enkelt refleks passage.

Key Design Decision

Snarere end kontinuerlig analog sensor læsning bruger systemet en tæller-baseret state machine hvor interrupts deaktiveres umiddelbart efter triggering og gen-aktiveres kun efter en timer udsøbt (debounce deatime). Dette giver præcis, støjfri positions tracking. Eksterne interrupts deaktiveres (EIMSK = 0b00000000) i ISR, forhindrer flere tællinger mens køretøjet stadig passerer over en refleks.

Main Functions

  • Initsensor() - Engangs konfiguration: muliggør INT0 og INT1 eksterne interrupt pinne, sætter kant trigger mode, konfigurerer interrupt mask register (EIMSK)
  • start_timer(uint16_t deadtime_ms) - Initierer Timer5 med specificeret deatime i millisekunder. Når timer udsøbt, ISR gen-aktiverer eksterne interrupts (EIMSK = 0b00000011)

Global State Variable

Refleks_count - Volatile unsigned char (0-9): sporer køretøjs position relativt til reflekser. Dette er den PRIØRE state variabel der kontrollerer hele system progression. Hoved-loop læser denne værdi for at bestemme hvilken tilstand der skal udføres.

Code Example

// ISR triggered when reflective strip passes sensor
ISR(INT0_vect) {
    Refleks_count++;              // Increment position counter
    EIMSK = 0b00000000;           // Disable ALL external interrupts
    
    // Adaptive debounce: high-speed states use shorter window
    if(Refleks_count == 7 || Refleks_count == 8) {
        start_timer(200);         // High-speed: 200ms debounce
    } else {
        start_timer(500);         // Normal: 500ms debounce
    }
    
    UNISendInteger(USART2, Refleks_count);  // Send count via UART
}

// Timer ISR (Timer5) - re-enables interrupts after debounce
// EIMSK = 0b00000011;  // Re-enable INT0 and INT1

Debounce Mechanism

Systemet genkender at en enkelt refleks passage optager tid mens sensor driver ind/ud af detektionsområde. Uden debouncing skaber dette flere interrupt triggers for en logisk hændelse. Løsningen: umiddelbart deaktiverer interrupts efter trigger, derefter gen-aktiverer efter en timer-baseret deatime vindue.

  • 500ms debounce (Tilstande 0-6) - Standard operation: sikrer køretøjet føldigtende passerer refleks før næste trigger muligværd
  • 200ms debounce (Tilstande 7-8) - Høj-hastighed operation: køretøjet bevæger sig hurtigere, kortere debounce forhindrer at misse næste refleks
  • Adaptiv timing - Dynamisk konfigureret i ISR baseret på Refleks_count værdi, optimering for forventet hastighed i hver tilstand

Problems Solved

Problem: Enkelt refleks forårsager 5-15 interrupt triggers mens sensor forvirrende detektionszone skaber gentagne kant transitioner.

Løsning: Debounce timer deaktiverer interrupts i fast varighed efter trigger, eliminering af falske tællinger og sikring af nøjagtigt en tælling pr refleks passage.

Problem: Fastsat 500ms debounce vindue for lang til høj-hastighed køretøj tilstande hvor reflekser passerer hurtigere.

Løsning: Adaptiv debounce timing i ISR - automatisk skifter til 200ms for høj-hastighed tilstande (7-8), sikring at ingen refleks mistes samtidig med vedligeholdelse af bounce beskyttelse ved lavere hastigheder.

UART Kommunikation - Serielgrænseflade til Kontrol og Telemetri Documentation

Purpose and Design

UART-driveren giver seriel kommunikation mellem mikrokontrolleren og eksterne systemer (menu grænseflade, debugging, telemetri). Den abstrakt lavniveau register manipulation bag en simpel initialisering og transmissions grænseflade.

Main Functions

  • InitUSARTArgs(USART_t *usart, uint16_t baudrate, uint8_t databits, uint8_t stopbits) - Konfigurerer specificeret USART perifer med baud rate, data bit tælling og stop bit tælling
  • UNISendInteger(USART_t *usart, int value) - Transmitterer heltal værdi som ASCII tekst streng over UART seriel linje

Code Example

// From main.c - initialization at program startup
InitUSARTArgs(USART2, 9600, 8, 0);  // Configure USART2: 9600 baud, 8 data, 0 stop

// During sensor ISR - transmit reflector count
ISR(INT0_vect) {
    Refleks_count++;
    UNISendInteger(USART2, Refleks_count);  // Sends "1", "2", ... "9" as text
    // Terminal receives: "1\r\n1\r\n2\r\n2\r\n3" etc.
}

// Menu system uses UART for user interaction
_menuSYS(USART2);  // Displays options and reads user input from serial

Technical Specifications

  • Baud Rate - 9600 bits/sekund (9600 baud)
  • Data Format - 8 bits pr tegn, 0 stop bits
  • Interface - USART2 perifer på AVR mikrokontroller
  • Kommunikationstype - Asynkron seriel, blokerende transmision

Menusystem - Bruger Interface og Kontrollogik Documentation

Purpose and Design

Menusystemet giver en tekst-baseret brugerinterface over UART til test og kontrol af køretøj drift. Det kører i hoved-loop under initialiserings fase og selektivt under autonom drift, muliggørende real-time debugging og manual intervention.

Main Functions

  • _menuSYS(USART_t *usart) - Hoved menu dispatcher: gentagne gange kaldet i hoved loop til visning af muligheder og udsendelse af bruger kommandoer
  • menu(USART_t *usart) - Menu visning og input capture: viser tilgængelige muligheder og læser bruger valg fra seriel
  • kontrole(USART_t *usart) - Kommando udførelse: baseret på menu valg, kalder passende driver funktioner (motor hastighed, lys, audio)

Operational Flow

Menusystemet opererer som en ikke-blokerende state machine der kører kun når Refleks_count er i specifikke tilstande (primært 0 under initialisering). Når sensor detekterer første refleks (Refleks_count inkrementer til 1), kan menu kaldes mellem state transitioner til debugging. Designet tillader autonom progression mens der forbliver responsivt til manuelle kommandoer.

// Main execution flow
// INITIALIZATION: Refleks_count == 0
while(Refleks_count == 0) {
    _menuSYS(USART2);  // Display menu, wait for user input
}

// STATE 1: Gradual Acceleration
SetForlys(150);  SetBaklys(100);  SetBaglys(0);
motorPWMGradvis(0, 200, 1, 1, 10);  // 0 → 200 PWM over 2 seconds
while(Refleks_count == 1) {
    _menuSYS(USART2);  // Menu remains available for debugging
}

// STATES 2-9: Progressive State Transitions
// Each state configures lights and motor differently
// Sensor detection increments Refleks_count, triggering next state

Test og Validering Documentation

Hardware Integration Testing

  • Motorcontrol - Verifikation af PWM output på oscilloskop; bekræftet glatte acceleration profiler ved hjælp af motorPWMGradvis() med varierende trin størrelser
  • Sensor detektion - Testning af interrupt triggering ved manuel refleks passage over sensor; bekræftet korrekt Refleks_count inkrementering
  • Lyskredsløb - Validering af uafhængig lyskontrol og PWM intensitets justering; måling af duty cycle på hver lys output
  • UART kommunikation - Bekræftet telemetri output over seriel terminal ved 9600 baud; verifikation af menu input/output flow
  • Interrupt timing - Verifikation af timer-baseret debounce ved hjælp af oscilloskop (indfanget interrupt deaktivering/aktivering timing); bekræftet forhindring af flere tællinger pr refleks
  • State transitioner - Bekræftet progression gennem alle 9 tilstande uden manuel intervention; validering af timing mellem refleks detektioner

Known Limitations

  • Fast refleks tælling - System antager nøjagtigt 9 reflekser på spor; tæller fortsætter forbel 9 hvis spor ikke stoppes
  • Menu under autonomy - Menu forbliver aktiv under autonom drift (ikke-blokerende men potentielt forvirrende)
  • Ingen fejlbehandling - Manglende fejl recovery til afbrudt sensorer eller fejlede motor initialisering
  • Blokerende UART - UNISendInteger() er blokering; høj-frekvens telemetri kunne forsinke motorcontrol med millisekunder
  • Ingen hastigheds feedback - Ingen encoder eller tachometer; motor hastighed estimeret fra PWM værdi kun

Test Equipment and Methods

  • Oscilloskop - Indfanget PWM bølgeformer til motor og lys; verifikation af interrupt timing og debounce vindue
  • Seriel Terminal (PuTTY) - Menu interaktion og telemetri overvågning ved 9600 baud
  • Manuel refleks positionering - Triggering af sensor ved passage af refleks over detektionszone
  • Strømforsyning med strømbegrænsning - Motor belastningstest med konfigurerbar strøm begrænsninger

Project Conclusion

Results

BIL-systemet arbejdede som forventet. Interrupt-drevet sensor håndtering med adaptiv debounce-timing eliminerede sensorbounce og optimerede for varierende køretøjhastigheder. PWM-baseret motorcontrol med glatte accelerationsprofiler forhindrede mekanisk stød og gav flydende hastighedsovergange. Uafhængig lyskontrol muliggjorde realistisk multi-circuit lysintensitetsmodulation. State machine progression drevet af præcis sensor positionering arbejdede pålidelig gennem alle 9 tilstande. UART-kommunikationen var stabil, og systemet bevarte fuld telemetri uden datatab. Projektets primære mål blev opnået: fuldt funktionelt autonomt køretøjkontrolsystem med robust interrupt-arkitektur.

Lessons Learned

Adaptiv debounce-timing er kritisk for interrupt-drevet design. Initialt brugte vi fastsat 500ms vinduer, men opdagede at høj-hastighed tilstande krævede kortere windows (200ms). Lektie 1: Tilstandsafhængig timing løste problemet bedre end én global værdi. Volatile globale variabler er essensielle for ISR-data. Vi erfarede at compiler-optimering fjernede læsninger hvis Refleks_count ikke var volatile, hvilket fik state machine til at hænge. Lektie 2: Memory barriers og volatile keywords er ikke valfri i embedded ISR design. Non-blokerende menusystem er vigtig under autonom operation. Initialt ville vi blokere menuen, men det forhindrede sensor interrupt håndtering. Redesign til polling-baseret menu tillod samtidig sensor og bruger-input. Lektie 3: Blokering i ISR-kontekst er farligt; alt skal være interrupt-safe. Hardware-timing kan ikke afhænge af software estimates. Vi antog 10ms PWM-trin ville give glat acceleration, men oscilloskop-måling viste variabilitet. Timere-baseret acceleration i stedet for loop-counts gav konsistent adfærd. Lektie 4: Validér timing-kritiske operationer med hardware-instrumenter. Modularisering af drivers reducerer debug-tid væsentligt. Isolerede test af motor, lys og sensor var langt lettere end at teste det samlede system først. Lektie 5: Hver driver-modul skal være selvstændigt testbar før integration.

Future Improvements

  • Encoder-baseret feedback: Tilføj rotationsencodere til motormodulet for høj-præcision position-tracking uden at stole på statiske reflekser
  • Forhindringsgenkendelse: Ultrasoniske sensorer for autonome navigationsforbedringer
  • Telemetri logging: SD-kort integration for opsamling af historik til post-analysis
  • Trådløs kontrol: Bluetooth- eller RF-modul til fjernbetjening uden seriel kabel
  • Energistyring: Batteri-monitor og low-power sleep-modes til øget autonomi
  • Fejlgendannelse: Timeouts og watchdog-timer for at håndtere sensor-fejl gracefully
